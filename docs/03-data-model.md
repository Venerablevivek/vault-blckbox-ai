# 03 — Data Model

Six tables, exactly as the blueprint's §4 specifies. PostgreSQL, raw SQL, no ORM. All ids are
`uuid` generated by the application. All timestamps are `timestamptz`, always UTC.

---

## ERD

```
   users ────────────< sessions
     │
     │                                        N
     ├──────< workspace_members >──────────────  workspaces
     │           (role: OWNER|MEMBER)               │
     │                                              │
     ├──────< invitations >─────────────────────────┤
     │           (email, role, token_hash)          │
     │                                              │
     └──────< documents (uploaded_by) >─────────────┘
                   │      (storage_key → MinIO object)
                   │
                   └──────< shares >
                              (token_hash, expires_at, revoked_at)
```

`sessions` is the one table beyond the blueprint's list — the blueprint mandates *"server-side session
cookie"*, which requires somewhere to put the session. Noted rather than smuggled in.

## DDL

### `001_users_sessions.sql`
```sql
CREATE TABLE users (
  id            uuid PRIMARY KEY,
  email         text NOT NULL UNIQUE,          -- lowercased at the application boundary
  password_hash text NOT NULL,                 -- argon2id
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  id         uuid PRIMARY KEY,
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash bytea NOT NULL UNIQUE,            -- sha256(token); plaintext is never stored
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX sessions_user_id_idx    ON sessions (user_id);
CREATE INDEX sessions_expires_at_idx ON sessions (expires_at);
```

Emails are lowercased in the application rather than using `citext` — one helper, no extension, no
surprise for whoever reads the SQL.

### `002_workspaces_members.sql`
```sql
CREATE TABLE workspaces (
  id         uuid PRIMARY KEY,
  name       text NOT NULL,
  created_by uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TYPE workspace_role AS ENUM ('OWNER', 'MEMBER');

CREATE TABLE workspace_members (
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  user_id      uuid NOT NULL REFERENCES users(id)      ON DELETE CASCADE,
  role         workspace_role NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (workspace_id, user_id)          -- the required unique(workspace_id, user_id)
);
CREATE INDEX workspace_members_user_id_idx ON workspace_members (user_id);
```

The composite primary key **is** the uniqueness constraint the blueprint asks for — the database
prevents duplicate membership, which is one of the five tests it names. `ON DELETE CASCADE` on both
sides means membership never outlives what it refers to.

`workspace_members_user_id_idx` backs "list my workspaces", which runs on every page load.

### `003_documents.sql`
```sql
CREATE TABLE documents (
  id           uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  uploaded_by  uuid NOT NULL REFERENCES users(id)      ON DELETE RESTRICT,
  filename     text NOT NULL,
  storage_key  text NOT NULL UNIQUE,
  mime_type    text NOT NULL,
  size         bigint NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz
);
CREATE INDEX documents_workspace_live_idx
  ON documents (workspace_id, created_at DESC) WHERE deleted_at IS NULL;
```

`workspace_id NOT NULL` is the schema-level expression of the central decision: there is no document
outside a workspace, so there is no second authorization path.

`storage_key UNIQUE` guarantees no two rows ever point at the same object — so deleting one document
can never remove another's bytes.

The partial index is the required `workspace_id` index, filtered to live rows because every listing
query filters the same way.

### `004_shares.sql`
```sql
CREATE TABLE shares (
  id          uuid PRIMARY KEY,
  document_id uuid NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  token_hash  bytea NOT NULL UNIQUE,           -- sha256(256-bit token); plaintext never stored
  expires_at  timestamptz,                     -- NULL = never expires
  created_by  uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  created_at  timestamptz NOT NULL DEFAULT now(),
  revoked_at  timestamptz
);
CREATE INDEX shares_document_id_idx ON shares (document_id);
```

`token_hash UNIQUE` is both the integrity constraint and the lookup index — resolving a link is a
single indexed read of a hash.

### `005_invitations.sql`
```sql
CREATE TABLE invitations (
  id           uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  email        text NOT NULL,                  -- lowercased; the invite is bound to this address
  token_hash   bytea NOT NULL UNIQUE,
  role         workspace_role NOT NULL,
  expires_at   timestamptz NOT NULL,
  accepted_at  timestamptz,
  created_by   uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX invitations_pending_idx
  ON invitations (workspace_id, email) WHERE accepted_at IS NULL;
CREATE INDEX invitations_email_idx ON invitations (email);
```

The partial unique index means re-inviting the same address replaces rather than duplicates. Single
use is `accepted_at IS NOT NULL`.

### `006_share_access_events.sql`
```sql
CREATE TABLE share_access_events (
  id          uuid PRIMARY KEY,
  share_id    uuid  NOT NULL REFERENCES shares(id) ON DELETE CASCADE,
  accessed_at timestamptz NOT NULL DEFAULT now(),
  ip_hash     bytea NOT NULL,          -- sha256(pepper || ip); never the address itself
  user_agent  text,
  outcome     text  NOT NULL
    CHECK (outcome IN ('resolved','downloaded','expired','revoked','document_deleted'))
);
CREATE INDEX share_access_events_share_idx ON share_access_events (share_id, accessed_at DESC);
```

Added for the product improvement — see [`09-product-improvement.md`](09-product-improvement.md).

The column that matters most is the one that is **absent**: there is no `ip` column. The visitor
opening a share link is not our user and never agreed to be tracked, so only a keyed hash is kept —
enough to count distinct viewers, useless for identifying anyone. `ON DELETE CASCADE` means the
history dies with the link, and with the document.

The `CHECK` constraint keeps `outcome` honest: a typo in application code becomes a failed insert
rather than a silently uncountable row.

### `007_audit_events.sql` and `008_notifications.sql`

`audit_events(workspace_id, actor_user_id NULL, action, resource_type, resource_id, metadata jsonb, created_at)`
— indexed on `(workspace_id, created_at DESC)`. `resource_id` has **no foreign key**, so deleting a
document cannot erase the record of it; the filename is snapshotted into `metadata`. Anonymous share
access has a null actor. Workspace deletion still cascades (there is no workspace deletion route).

`notifications(user_id, workspace_id, type, title, body, resource_id, read_at, created_at)` — indexed
on `(user_id, created_at DESC)` plus a partial index `WHERE read_at IS NULL` backing the unread badge,
which is polled every 20 seconds. `markRead` always filters on `user_id`, so one user cannot touch
another's rows.

## Transactional updates

The blueprint asks for *"foreign keys and transactional updates where related rows must change
together."* Three places qualify:

| Operation | Rows that must move together |
| --- | --- |
| **Register** | `users` + `workspaces` + `workspace_members` (the auto-created first workspace) |
| **Accept invitation** | `workspace_members` INSERT + `invitations.accepted_at` UPDATE — and, if the user is registering from the invite, the `users` row too |
| **Create workspace** | `workspaces` + the creator's OWNER `workspace_members` row |

All three use `withTransaction(fn)`. Accepting an invitation twice is prevented by
`UPDATE invitations SET accepted_at = now() WHERE id = $1 AND accepted_at IS NULL RETURNING *` —
zero rows means already accepted, checked before the membership insert. The composite primary key on
`workspace_members` is the backstop.

## Lifecycles

**Document**
```
upload → object written to MinIO → row inserted
   │        └─ row insert fails ──> object deleted, request fails (no metadata persisted)
   │
   └─ delete ─> deleted_at = now()  [committed]  ──> object deleted from MinIO
                  │
                  ├─ invisible to listing, download and share resolution, immediately
                  └─ object delete fails ──> logged with the key at error level
```

**Share link**
```
active ──expires_at passed────────> 410
   ├───revoked_at set─────────────> 410
   └───document soft-deleted──────> 410   (re-checked on every resolve, never cached)
```

**Membership**
```
invited ──accept (one tx: insert member + stamp accepted_at)──> member
    ├── expires (7d) ──> expired
    └── email mismatch ──> rejected, invite stays pending
workspace deleted (not exposed in the API) ──> memberships cascade
```

## Queries worth calling out

```sql
-- The authorization lookup. Runs on every workspace-scoped request. PK lookup.
SELECT role FROM workspace_members WHERE workspace_id = $1 AND user_id = $2;

-- Resolving a share link. One indexed read; every liveness rule checked in SQL,
-- including the document's soft-delete state, so a deleted document kills its links instantly.
SELECT s.id, d.id AS document_id, d.filename, d.mime_type, d.size, d.storage_key
  FROM shares s
  JOIN documents d ON d.id = s.document_id
 WHERE s.token_hash = $1
   AND s.revoked_at IS NULL
   AND (s.expires_at IS NULL OR s.expires_at > now())
   AND d.deleted_at IS NULL;

-- Single-use invitation acceptance. Zero rows == already accepted. No read-then-write race.
UPDATE invitations SET accepted_at = now()
 WHERE id = $1 AND accepted_at IS NULL AND expires_at > now()
RETURNING workspace_id, email, role;
```

Every one is parameterized: user input never reaches SQL text. The only interpolations into a query
string are fixed fragments: the file-type `CASE` expression in `overview.service.ts`, and the sort
expressions in `documents.repo.ts`, chosen from a whitelist (`SORT_SQL`) by an enum-validated key.
This is checked by review; there is no lint rule enforcing it.
